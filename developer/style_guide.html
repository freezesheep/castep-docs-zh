    代码风格指南

    中文译文 · 由本地英文文档翻译，已统一术语并进行重点抽查。 英文原文对照 · 翻译说明

    简介

    CASTEP 程序自设计之初就旨在实现多种目标——包括高效性和可维护性。以下是一些关于编写 CASTEP 代码的简单指导原则。这些原则旨在帮助编写正确且高效的代码，并确保多位作者在代码中保持一致的风格，以便未来其他人员能够轻松维护。所有代码将使用 Fortran 2003 作为编程语言，因为该语言具备许多现代特性，能够在不牺牲效率和可移植性的前提下，编写出简洁、模块化的代码。

    在本文档中，有一个 编写模块的模板，以及在模块内编写子程序时使用。这些模板旨在强制执行良好的编程实践和对例行程序功能及副作用的文档说明。所有程序必须使用这些模板编写。本文中提到的关于风格的一般准则、模块模板的使用、文档的完整性等方面，都有助于使编写新代码和维护现有代码变得简单。

    程序员还有责任尽可能高效地编写每个子程序。虽然使用 Fortran 2003 的新内置功能很有吸引力，但经验表明，应谨慎使用这些功能，以免降低运行效率。因此，文档也给出了使用这些功能的指导原则。

    CASTEP 检查工具

    CASTEP 检查工具是一个 Python 工具，用于检查您的 CASTEP 构建是否存在与 CASTEP 风格相关的任何问题。在进行任何重大修改后应使用该工具。

    说明

    linters 也在 CASTEP CI 系统中运行，如果您的修改引入了新的问题，它会向您发出警告。如果您的拉取请求中包含新问题，该请求可能会被拒绝。

    使用 CASTEP 检查工具

    语法检查工具可在 PyPI 并且可以使用 pip:

    python -m pip install castep-linter

    安装完成后，应可以通过运行以下命令来执行检查工具：

    castep-lint <file>

    e.g.

    castep-lint Source/Functional/pair_pot.f90

    如需进一步信息，请输入

    castep-lint -h

    也可以在以下编辑器中使用 CASTEP 静态检查工具： Emacs ，通过 flycheck 扩展实现。为此，必须安装 flycheck 软件包，该软件包可通过 MELPA Emacs 软件包仓库安装。

    写入规范文档

    “它确实如其名所示。”

    显然，首要任务是确保你负责的每个子程序都严格执行规范规定的行为，尤其要注意退出条件、副作用等。

    规范涵盖的子程序和变量为 public ，而其他子程序和变量为 private规范中并未说明私有例程的作用或含义。私有例程和变量仅在其出现的模块内可访问。

    不要假设规格文档中未写明的内容

    如果规范中未说明某个子程序在退出时会保留输入值，那么你不能假设编写该子程序的人会这样做！即使该子程序是你自己编写的……

    同样，即使某个变量的含义看似显而易见，只要规范未作定义，就不能自行假定。后续代码修订可以自由修改规范之外的子程序。如果所有代码始终遵循规范，维护工作就会简单得多。

    请注意，规范中并未提及任何模块中的私有子程序或变量。因此，在使用此类子程序时必须格外小心。 子程序模板 是否有提醒你记录每个例行程序的所有副作用！

    代码应稳健地处理错误

    也就是说，用户永远不应该看到Fortran运行时错误消息——你的代码应检查可能的错误情况，并要么纠正错误，要么打印一条清晰且有意义的错误信息，然后通过优雅退出来结束程序。 io_abort.

    执行条件

    规范中给出的条件必须为真，才能正确执行每个子程序。显然，这些条件应当被检验以确保正确性，但这样可能会引入相当大的性能开销，特别是对于 Utility 或者 Fundamental 子程序。因此，建议使用单一 #ifdef debug 每个例程开头的块用于测试这些条件（在适当情况下）并调用 io_abort 必要时。然后可以根据需要编译带有或不带完整错误检查的代码。

    错误与警告

    使用 stderr 从任意节点

    与普通消息不同，任何节点都可以写入错误或警告消息。任何此类消息都应写入到 stderr 从相关节点获取。该例程随后将调用 io_abort 以便整洁地终止程序。

    使用 iprint 一致地

    正常输出，包括警告信息和调试信息，应仅写入到 stdout 由根节点处。细节程度由以下内容控制 iprint 变量：

    • 0 - 最小输出 - 仅包含运行控制参数和结果！

    • 1 - 默认输出 - 将能量和力分解为各个组成部分等，但不包含调试信息。

    • 2 - 最小化调试 - 所有重要参数的值等，不打印所有数组。

    • 3 - 最大化调试 - 工作开始了！

    效率问题

    库

    建议使用 BLAS 和 LAPACK 库，因为这些是免费可用的库，并且通常针对每个平台提供了厂商优化版本。为了提高效率，也建议不要使用 BLAS 的“级别 0 子程序”，因为其性能提升微乎其微，而对应的 FORTRAN 代码往往更简洁、更容易阅读。

    Fortran 数组内建函数

    注意使用 FORTRAN 数组内建函数——它们可能效率低下，并可能导致内存问题，例如 result=matmul(a,matmul(b,c)) 需要隐式动态内存分配。在可行的情况下，尽量使用 BLAS。某些内建函数也可能阻碍编译器优化，尤其是在向量机上。同样，不要使用诸如……的函数。 transfer 或者 mold — 这些可能非常低效。

    将数组传递给子程序

    这是一个棘手的主题，很容易导致混淆和低效的代码。主要问题是存在多种传递数组的方法，而这些方法通常并不等价！

    最佳做法是始终一起传递整个数组及其大小，例如：

    call foo(int_array, N1, N2)
...

subroutine foo(int_array, N1, N2)
implicit none
integer, intent(in) :: N1, N2
integer, dimension(1:N1, 1:N2) :: int_array
...

    由于这不会导致数组的复制，并允许编译器进行边界检查等操作。

    使用 假设形状数组，例如 int_array(:, :) 效率较低，因为其具有显式的秩，但隐式的形状。这需要使用诸如函数 size(int_array,1) 并且可能会阻止某些编译器优化。然而，它允许编译器进行边界检查。

    在传递数组时必须小心。如果要传递数组切片，则最好使用 假设大小的数组 （即传统方式），也就是说

    call foo2(int_array(1, N))
...

subroutine foo2(int_array)
implicit none
integer, dimension(*) :: int_array
...

    不如直接通过 int_array(:, N) 并接收 int_array(:) 这将会在栈上创建数组的副本，从而迅速导致“内存不足”错误。

    使用预设大小的数组，例如 int_array(*) 如果想编写一个通用程序，能够处理任意大小和/或维度的数组，则该功能是有用的。然而，它通常不适用于标量，也不支持边界检查。不过，它不会导致数组的任何副本被创建。

    特定机器的代码

    避免！

    使用标准Fortran编写，避免使用厂商扩展，并尽可能不使用任何系统例程，以确保最大可移植性。唯一被允许的例外出现在 Utility 模块，其中所有低级别的输入/输出和通信均被处理。

    仔细测试以防止

    务必在多个平台上使用多种编译器测试子程序，确保没有无意中依赖某个编译器特有的默认行为。向 Bitbucket 仓库提交合并请求后，CI 系统会使用所有受支持的编译器进行编译；但为减少排错工作，应在提交之前完成这些测试。

    文件处理

    一个明显的机器依赖领域是文件处理。因此， io 应使用模块来处理所有文件的打开操作。程序员需负责读取/写入数据以及关闭文件。文件不应被保持打开状态，除非绝对必要。

    编译器/预处理器指令

    这些应尽可能避免，因为它们会妨碍可移植性。它们只应在以下情况下使用 Utility 用于特定机器代码的模块。所有模块文件名都应添加扩展名 .f90，例外的是 Utility 模块，其中 .F90 是被允许的，但通常只有在使用预处理的情况下才如此。

    Fortran90 特性

    动态数组的使用

    每个例程负责分配/使用/释放其自身的工作空间。我们建议此类 allocate/deallocates 仅在例行程序中出现一次——绝不要放在循环内部，否则会造成显著的性能损失。你必须确保它始终 deallocate 局部工作数组在例行程序终止时的处理。显然，如果一个例行程序有多个退出点，则需要格外小心。

    指针

    始终将子程序中的传入数组视为数组，而非指针。这将强制编译器对数组进行自动解引用，并使编译器能够实现更好的优化。

    控制流

    构造如 select case 并且 do ... end do，并使用“do循环”等标注以增强清晰度，推荐采用 cycle 并且 exit 可以使用，但应尽可能只跳出一层嵌套。不要使用 goto.

    函数

    函数子程序应是“纯”的，即不能通过修改实参列表中的变量，或修改经 USE 关联访问的模块变量来产生副作用。避免递归。

    使用 use

    如果只需要少量变量，在使用模块时应加上 only 子句。将适当的 use 语句放在需要它的各个子程序中，而不是模块头部，以便追踪模块变量的修改。

    行号

    尽可能避免使用。行号仅用于格式语句，以及 end= 或者 err= 文件处理。不要使用 continue.

    一般特性

    除非语句极其简单，否则避免在同一行中放置多条语句。

    模块

    常规设置

    所有代码都应包含在模块内。

    用法

    规范中描述的每个模块应为一个源文件。本模块规范中给出的所有例程都应包含在该文件中。

    辅助模块

    CASTEP 也鼓励使用较新的（Fortran 2008） submodules. 子模块允许对模块进行程序化划分，从而使得编译器可以预先编译接口、在仅子模块发生更改时减少必要的编译操作，并使开发者能够更有效地控制模块内部的范围。

    为清晰起见，并避免模块过长，该模块也可使用辅助模块，这些辅助模块可以位于单独的文件中（同样每个模块一个文件）。任何辅助模块必须仅在指定的一个模块中使用，即不允许在其他指定模块中重复使用辅助代码，因为辅助程序并未被明确指定！

    任何辅助模块的命名规范应继承自指定模块，以明确辅助程序的应用位置，例如，如果指定模块被称为 me.F90 带有称为的子程序 me_sub，等等。那么一个辅助模块就会 me_extra.F90 带有称为的子程序 me_extra_sub，等等。

    说明

    与其在现代CASTEP中使用完整的辅助模块， submodule被鼓励。

    风格与布局

    使用模块模板

    模块模板 给出了模块和子程序的推荐布局。该内容可在 CASTEP 源代码中找到。 Source/template.f90特别是，请注意注释头的布局和内容，以及声明的顺序。除非明确指定为公共成员，否则所有内容都应为私有！这使得代码与规范之间的对比检查变得简单。

    布局

    所有代码均应使用 GNU-Emacs f90-mode 生成的缩进格式。您可以使用任何编辑器编写代码，但请确保最终提交到 Bitbucket 仓库的代码都已通过 Emacs f90-mode 进行过缩进处理。为帮助您更好地使用 Emacs， 模块模板 包含设置 f90-mode 等的 Emacs 指令。

    情况

    使用小写字母表示关键词，所有在规范中提及的例程和变量的大小写应按规范给出。对于私有例程和变量，一般使用小写字母。然而，你可以使用大写字母来区分名称中的单词，例如 userInputData — 只要你在整个模块中保持一致即可。

    使用大写，且去掉空格，用于在各程序模块之间传递的字符串变量值，例如 run_type='MOLECULARDYNAMICS' 不是 'MolecularDynamics' 或者 'molecular dynamics' 等等以简化字符串比较。

    名称

    为清晰起见，尽可能不更改变量名称以传递到不同的子程序中。除非是简单的循环计数器，否则避免使用短（1或2个字母）的变量名。采用新形式 end subroutine name 等等，不是旧版本 end subroutine.

    类型

    不要使用隐式类型。同样，你不必遵循旧的隐式类型规则——你可以使用以“”开头的整数名称。c等等！不要将类型标注为 double precision - 使用 real(kind=dp) 相反，作为 dp 是 Constants 模块中的一个常量，这将使移植到其他架构（例如 Cray）变得简单得多。请记住，所有与机器相关的代码都保留在 Utility 子程序中。同样，在声明常量时，请使用 1.234_dp NOT 1.234d0.

    自由格式

    使用自由格式f90，最大行长度为132个字符。

    空间

    在关键词之间使用空格，例如 end if 不是 endif.

    代码整洁

    显然，为了确保正确性并便于他人维护代码，如果编写一个子程序的显而易见方法效率低下，而高效的方法又晦涩难懂，则只要该子程序内部有充分的文档说明，并对所作的设计决策进行讨论，这种情况也是被允许的。

    请注意向量化处理

    编程时，请注意代码几乎总是运行在向量架构上。因此，应编写能够良好实现向量化处理的代码——例如，不要将 if 在嵌套循环中尽可能将语句放在内部。

    使用文档

    内部

    每个模块基于 模块模板，应包含一个描述其整体目的和功能的头部区块。

    每个编写到模板中的例程都应包含一个头部块，描述其功能、所需变量及其修改方式、正确运行所必需的条件等。这些注释应当清晰明了，易于理解。

    每个例程的代码中都应包含大量注释。注释要么与被注释的特征位于同一行（或几行），要么位于该特征上方的一段连续行内。

    注：密度应与代码密度相当。

    所有评论须用英文书写，并符合标准英语语法规则。

    外部

    一个模块（或任何修改）只有在提供了额外的文档以供包含时，才被视为完整。文档必须提供在相应的模块和函数头文件块中，解释该模块及每个子程序的功能、代码背后的物理原理、所采用的算法、关键变量和数据结构，并适当引用相关文献。

    测试

    测试程序

    每个模块在被添加到 Bitbucket 仓库之前，都必须经过正确性测试。为此，应提供一组测试用例，这些测试用例必须能够在 CI 系统中成功编译和执行。这些测试的目的是验证模块中每项指定子程序的正常运行。

    CASTEP 使用的 testcode 一个测试平台，可从一组有效的 CASTEP 输入文件自动生成基准数据。

    请参见 测试 有关如何完成此操作的更多信息。

    参考数据

    测试程序应附带适当的输入数据文件和参考输出结果。通过将实际输出与参考输出结果进行比较，以验证测试的正确运行。

    模块模板

    常规设置

    请注意声明的顺序，以及使用 implicit none 并且 private，以及标准的注释标题，用于内部文档。注释标题中的所有行宽度应为80个字符。并非所有标题部分对所有子程序都相关，因此可以删除不相关的部分。非常重要的是，标题必须始终保持最新且尽可能完整。

    使用 public 并且 private

    每个模块使用一个初始值 private 声明强制模块中的所有实体默认为私有。然后具有显式 public 声明那些在规范文档中列出的数据类型、变量和（重载的）过程名称。这使得代码与规范文档的对比变得容易。
