    CASTEP 的测试套件

    中文译文 · 由本地英文文档翻译，已统一术语并进行重点抽查。 英文原文对照 · 翻译说明

    概述

    CASTEP 源代码分发包包含一个测试套件，以帮助开发者和用户或高性能计算（HPC）管理员。

    • 确保新开发和重构代码不会导致崩溃或显著改变任何结果；
    • 测试新编译器或现有编译器的新版本，检查语言标准支持、不可移植代码或编译器自身缺陷所引起的问题；
    • 确保串行和并行运行得到相同结果；
    • 实现测试自动化，使开发人员或 Jenkins 持续集成（CI）系统能够将测试作为日常开发的一部分执行。

    我们采用的测试方法称为 回归测试 ：使用大量适用于小规模计算的输入文件运行 CASTEP，并将结果与事先生成且已知正确的输出进行比较。这些输出称为每项测试的 基准结果 。自动化和测试通过以下平台完成： testcode 测试平台。它负责测试类别的定义、测试的选择与排序、执行测试，以及将运行结果与基准结果比较。为运行 CASTEP、后处理输出并提取比较数据，它会调用 CASTEP 发行版中随附的两个脚本，这两个脚本位于 bin 目录，名称为 run_castep_test.py 并且 extract_results.pl.

    该软件套件的目录结构包含一个顶层 Test 包含测试代码配置文件的目录，一个 GNU Makefile，其中包含用于驱动测试的目标，以及将测试分为不同类别的若干子目录；概要

    Test
 |-- CMakeLists.txt
 |-- Makefile
 |-- jobconfig
 |-- userconfig
 |-- Electronic
         |-- Cr-AFM
             |-- Cr_00PBE.uspcc
             |-- Cr_AFM.cell
             |-- Cr_AFM.param
             |-- benchmark.out.castep-23.1.castep-python-1.0.python-3.6.9.inp=Cr_AFM.param
         |-- <Electronic test 2> 
|-- <Category 2>
         |-- <Category 2 test 1>
         |-- <Category 2 test 2>
 ...

    测试你的代码

    一次完整的测试运行

    通过运行测试代码脚本启动测试套件的运行 <CASTEP_ROOT>/bin/testcode.py 从 Test 目录内出发，但因为一些选项通常需要启用，因此最方便的方式是通过构建系统使用以下方法：

        cd Test
    make check

    或者

        cmake -t check

    在使用 GNU make 或 CMake 构建系统进行编译后，将生成一段简要的输出信息，内容大致如下：

    make check COMMS_ARCH=mpi
Found mpirun, using PARALLEL_CMD=mpirun -np tc.nprocs
rm -f */*/*.castep */*/*.dfpt_wvfn */*/*.fd_wvfn */*/*.wvfn.* */*/*.*.err
../bin/testcode.py -q  --processors=4 --total-processors=36 --user-option castep run_cmd_template "../../../bin/run_castep_test.pl tc.program tc.args tc.input tc.output mpirun -np tc.nprocs" -e /home/user/CASTEP-23.1/bin/castep.mpi -c simple -c d3-simple -c d4-simple -c md-parallel
....................................................................................................................................................................................................................................................................................................................................................................................................................................................................................................... [487/487]

    如果所有测试均通过。如果一个或多个测试失败，则对应 . 被替换为一个 F 符号，或一个 S 用于标记该测试被跳过（可能是由于前置测试失败）。

    在测试失败的情况下，有关哪些测试失败以及失败原因的更详细信息，命令 make compare, make diff, cmake -t compare，或 cmake -t diff 将打印失败测试的摘要或详细分析到标准输出（stdout）。更深入的分析可能需要直接查看相应的 <test.out-...> 文件，在 Test/<category> 子目录，将包含的 .castep 输出以及 .0001.err 错误/回溯报告文件，在出现异常时 io_abort.

    部分测试与增量测试

    在代码开发过程中，运行整个测试套件以检查每一次变更将耗费过多时间且功能上不必要。测试被划分为若干类别，并命名为 spe ,bs ,geom ,md ,magres ,misc ,pair-pot ,phonon ,otf ,pseudo ,tddft ,ts ,xc ,nlxc ,libxc ,solvation ,d3 ,d4 ,python 并且 parallel 大致对应于子目录

    Test/
  |-Electronic
  |-Excitations
  |-Geometry
  |-MD
  |-Magres
  |-Misc
  |-Pair-Pot
  |-Phonon
  |-Pseudo
  |-TDDFT
  |-XC
  |-Solvation
  |-Dispersion
  |-Pseudopotentials
  |-Python
  |-Utilities
  |-LibXC
  |-Parallel

    并且可以单独使用运行

        make check-<category>
    make compare-<category>
    make diff-<category>

    或 CMake 中同名目标。

    运行单个测试

    事实上，测试可以以更细粒度进行，甚至细化到子目录级别。这并非通过 Makefile 或 CMake 实现，只能通过调用命令来访问。 testcode 直接如所述 如下然而最直接的方法是复制并粘贴测试代码调用命令，该命令由 make check-spe 包括所有运行和参数设置，并修改参数的 -c 选项以 <directory>/<subdirectory>.

    添加或修改测试

    代码可持续性要求，在开发任何新功能或扩展现有能力时，测试套件也应得到增强，以测试任何新的输出。

    所需的变化是

    • （可选）一个新的测试子目录。该目录将被自动扫描由 testcode 并且，如果它属于其中一个现有主要类别下的子目录，则应包含在内。如果新的输出是对现有功能的增强或选项，那么将其添加到现有的二级子目录中可能是合适的。
    • 当添加是一项重大新功能时，可能适合增加一个新的顶级类别和子目录树。在这种情况下 Makefile 并且 CMakeLists.txt 将需要扩展以添加新的 check, compare, diff 并且 recheck 目标。
    • CASTEP 输入文件： .cell 并且 .param
    • 如果需要任何外部赝势文件，这些文件应放置在 Test/Pseudopotentials 子目录，并从测试子目录创建一个符号链接。两者都应添加到 git 仓库。
    • 修改 bin/run_castep_test.py 如果你需要测试一个新输出文件的内容。
    • 如果测试一个新的量，无论是位于 .castep 文件或任何其他输出文件，你必须扩展该 bin/extract_results.pl 脚本用于查找并报告待测试的新值。
    • 一段新的诗行在 jobconfig 将需要指定比较的容差，如果使用默认值的话 userconfig 并不合适。

    • 一个包含已知良好运行的CASTEP输出的新基准文件。不幸的是，创建基准文件仍需要一些手动干预。遗憾的是 testcodes 选项创建新基准不合适，因为它过于僵化，无法在不更新整个测试套件的情况下创建单个测试。最简单的方法是

      a. 运行 testcode，可以通过 Make 或手动方式执行。新的测试将失败，因为没有基准数据用于比较。

      b. 复制或重命名刚刚创建的测试文件 test.out.<date>?inp=<seedname>.param 到 benchmark.out.castep-<old-castep-version>castep-python-1.0.python-<old-python-version>.inp=<seedname>.param。其中 <old-castep-version> 并且 <old-python-version> 应选择以匹配现有 benchmark.out 其他测试的文件。

    选择新测试时的考虑因素。

    CASTEP 中的测试通常通过一次简短的运行定义（包含完整 .cell 并且 .param 文件）其为：

    • 足以证明相关功能的有效性
    • 短到运行时间不会显著增加
    • 足够稳定，使得每次运行的结果不会发生显著变化。

    说明

    这些计算不一定需要具有物理意义，通常也不应该如此，因为耗时较长。收敛不足通常是可接受的，而且往往必要。

    实现一个测试可能未充分收敛的运行稳定性的常见方法有两种或三种：

    1. 设置一个显式 random_seed 在 .param 文件
    2. 使用以下方式指定k点： %BLOCK KPOINT_LIST 而不是使用网格或间距。这避免了k点对称性缩减因硬件、编译器选项等因素而生成不同但等效集合的倾向。通常一个非常粗略的集合就足够了。
    3. 使用过松的值通常会适得其反。 ELEC_ENERGY_TOL 由于在基准测试和测试之间增加或移除一次SCF迭代，可能会导致力的变化足够大，从而引发测试失败。

    测试套件的分析

    测试套件成功运行后，可以生成一个时间剖面图，该操作由 GNU make 命令完成。

    make profile > profile.log

    哪个将按执行时间排序的测试列表写入到命名文件中。如果使用 cmake，该剖面无条件生成，并写入一个扩展名为 test-profile-all.log 或者 test-profile-<category>.log 在 Test/ 子目录。

    测试套件的组成部分

    直接调用 testcode

    对于串行运行，测试套件可以直接从命令行调用（带有 Test/ 作为当前目录）由

        ../bin/testcode.py -q --total-processors=6 -e <castep-executable> -c simple -c d3-simple -c d4-simple -c solvation-simple

    其中 -q 将详细程度设置为最小。 --total-processors=<n> 限制同时运行的测试最大数量， -c simple 指定了通用的核心测试集。其他 -c 选项指定CASTEP构建中的可选组件，应根据测试可执行文件链接的库进行选择。对于MPI并行测试，其调用更为复杂：

        ../bin/testcode.py -q  --processors=4 --total-processors=6 --user-option castep run_cmd_template "../../../bin/run_castep_test.py tc.program tc.args tc.input tc.output -- mpirun -np tc.nprocs" -e <castep-executable> -c simple -c d3-simple -c d4-simple -c solvation-simple -c parallel-simple

    这里，testcode 选项 run_cmd_template 正在被明确指定，覆盖了在 userconfig 为了添加 mpirun 选项用于 run_castep_test.py 脚本的选项。请注意字符串的引号使用以及 testcodes 变量的引用。 tc.program, tc.args, tc.input, tc.output 并且 tc.nprocs 哪个测试代码在调用之前会替换 run_cmd_template 命令。额外的 testcode 选项 --processors=<n> 指定传递给 mpirun 的最大 MPI 进程数，并添加额外的测试类别 parallel-simple 其中包含 MPI 测试。

    当以这种方式调用 testcode 时，该“category”参数的 -c 可以被其子目录的名称替代 Test，例如

        -c Phonon/Si2-raman

    将仅运行该子目录中的测试。

    测试输出与基准测试

    在测试套件运行过程中，各个测试通过一个包装脚本执行。 run_castep_test.py. 这控制了CASTEP的执行，并收集和附加该特定任务生成的任何额外输出文件。这种拼接格式用于测试输出（test.out-...) 以及基准文件（benchmark.out-...).

    调用是

        run_castep_test.py [-d|--dryrun] -[h|--helpme] <castep-executable> <param-file> <output-file> -- [<mpirun-cmd>]
    • <castep-executable> 是串行或并行 CASTEP 可执行文件的路径。
    • <param-file> 是 <seed>.param 用于测试运行。
    • <output-file> 是测试输出文件名；Testcode 的格式为如下形式 test.out.<date>-<count>.inp=<param-file>
    • <mpirun-cmd> 是可选的，位于其他由……标记的参数之后 --。这是命令 run_castep_test 将被调用以执行 <castep-executable> 并行计算——通常情况下 mpirun -np <nprocs>.

    userconfig 文件

    这是测试代码读取的两个配置文件之一（文档说明) 并设置测试代码的默认选项，包括调用 CASTEP 的运行命令以通过 run_castep_test.py 脚本的串行和并行版本。

    它还包含每个特定属性的默认容差值，这些值可在每次测试中单独覆盖。 jobconfig 文件。

    jobconfig 文件

    测试代码的第二个配置文件（文档说明指定类别及测试专属参数，包括默认属性容差的覆盖值以及所需并行度的说明。配置文件

    结构为 jobconfig 如下：

    # Run all tests on this folder and all subfolders with the given settings.
[Electronic/*]
run_concurrent = true # (1)
tolerance = (0.015,  None, 'Spin') # (2)

# Override the settings of the general folder for a specific case.
[Electronic/Si2-fine-grid]
tolerance = (0.0003, None, 'Energy'), (0.0003, None, 'PS_Energy')

[categories]
spe-simple           = Electronic/*
bs-simple            = Excitations/*
phonon-simple        = Phonon/*
...
simple               = spe-simple bs-simple phonon-simple [...]
...

    说明

    该 <path_to_tests> 可以包含通配符，或绝对路径

    说明

    所有路径都相对于位置而言 jobconfig 在 CASTEP 的情况下那就是 <root>/Test

    在计算结束时 jobconfig 文件中有一个部分称为 categories 其中包含 testcode 了解的类别列表。结构为：

    <category_name> := <path_to_tests>|<other categories>
    1. 启用在此文件夹内并行运行测试。
    2. 为给定设置容差 性质.

    添加到构建系统

    添加到 CMake

    为了使测试与……兼容 CMake 构建系统 你需要修改的 CMakeLists.txt 在 Test/CMakeLists.txt 将类别添加到第 157 行的列表中，该行内容如下：

    foreach (CASTEP_TEST_CATEGORY "spe" "bs" "phonon" ...)
  ADD_CATEGORY_TARGETS(${CASTEP_TEST_CATEGORY} TRUE)
endforeach()

    添加到 Make

    为了正确地将测试添加到 GNU make 构建系统 你需要修改的 Makefile 在 Test/Makefile 并且在多个地方添加类别。

    添加到列表中 .PHONY :

    .PHONY: check check-simple check-spe-simple ...

    并在五类测试任务各自对应的列表中创建条目：

    1. check
    2. recheck
    3. benchmark
    4. compare
    5. diff

    在目标被调用时调用你的测试，例如：

    check-solvation: exe-exists prepare-clean
    $(TESTCODE) $(QUIET_FLAG)  $(PARALLEL) -e $(CASTEPEXE) -c solvation-simple

    说明

    exe-exists 并且 prepare-clean 需确保 CASTEP 已编译，并在开始测试前清除任何旧的测试运行记录。
